Conceitos Essenciais — sem mistério

🪟
JFrame
Uma janela independente do Windows/Mac/Linux. O FormPrincipal e FormUsuariosListar são JFrames — cada um abre uma janela nova na tela.
📋
JDialog
Uma janela filha modal — bloqueia a janela pai até ser fechada. O LoginDialog e FormUsuarioEditar são JDialogs para forçar o usuário a interagir.
🔌
JDBC
Java Database Connectivity — a "ponte" entre o Java e qualquer banco de dados. Com JDBC, o Java envia SQL ao MySQL e recebe os resultados, tudo via código Java.
🛡
PreparedStatement
Forma segura de enviar SQL ao banco. Os ? são preenchidos separadamente — isso bloqueia SQL Injection, um ataque muito comum.
📄
ResultSet
É como uma tabela em memória com os resultados de um SELECT. Você percorre linha por linha com rs.next() e lê cada coluna com rs.getString().
⚡
ActionListener
Um "ouvinte de eventos". Quando o usuário clica em um botão, o ActionListener detecta o clique e executa um bloco de código — é como instalar um campainha que toca quando algo acontece.
📊
JTable / DefaultTableModel
JTable é a grade visual de linhas e colunas. DefaultTableModel é o conjunto de dados por trás dela. Você alimenta o modelo, e a tabela exibe automaticamente.
🧵
SwingUtilities.invokeLater
O Swing tem uma regra: toda interface gráfica deve ser criada em uma thread especial chamada EDT. O invokeLater garante isso — sem ele, podem ocorrer bugs visuais aleatórios.
🔌Como o JDBC funciona — do Java ao MySQLJDBC

Quando o Java precisa buscar ou salvar dados, ele abre uma Connection (canal direto ao banco), prepara um PreparedStatement (o SQL com ? como placeholders), preenche os ? com os valores reais, executa a query e recebe um ResultSet com os resultados.

Cada Connection aberta consome recursos do banco. Por isso, todo código de banco do projeto termina com rs.close() → stmt.close() → conn.close(). Esquecer de fechar a conexão é como deixar a torneira aberta — eventualmente o banco fica sem "água".

🪟Como o Swing funciona — componentes e eventosSwing

O Swing monta interfaces empilhando componentes (JButton, JTextField, JLabel, JTable...) dentro de painéis (JPanel) que ficam dentro de janelas (JFrame/JDialog). Cada componente pode ter listeners que disparam código quando o usuário interage.

Os LayoutManagers controlam como os componentes se posicionam. O BorderLayout divide a janela em Norte/Sul/Leste/Oeste/Centro. O GridBagLayout dá controle fino de posição — linha, coluna, espaçamento — como uma planilha.

Conexao.java — A fábrica de conexões

Esta é a classe mais fundamental do projeto: sem ela, nenhuma outra classe consegue falar com o banco de dados.

Conexao.java
package javasistema;                                                    // linha 1
import java.sql.Connection;                                             // linha 3
import java.sql.DriverManager;                                          // linha 4

public class Conexao {
    private static final String URL = "jdbc:mysql://bd_savir.mysql...";  // linha 7
    private static final String USUARIO = "bd_savir";                   // linha 8
    private static final String SENHA = "B@nc0D@d0s";                  // linha 9

    static {                                                               // linha 11
        try {
            Class.forName("com.mysql.cj.jdbc.Driver");                   // linha 13
        } catch (ClassNotFoundException e) { ... }
    }

    public static Connection getConnection() throws Exception {        // linha 20
        return DriverManager.getConnection(URL, USUARIO, SENHA);          // linha 21
    }

    public static boolean testarConexao() {                             // linha 26
        try (Connection conn = getConnection()) {
            if (conn != null) { return true; }
        } catch (Exception e) { ... }
        return false;
    }
}
L1
package javasistema;
Declaração de pacote — organizando o projeto
package é como uma "pasta lógica" no Java. Todas as 9 classes do projeto pertencem ao pacote javasistema, o que significa que elas podem se enxergar e usar umas às outras livremente sem importações extras.

Sem essa declaração, o Java trataria cada arquivo como uma classe isolada e não saberia que elas pertencem ao mesmo sistema.
É como colocar todos os arquivos de um departamento na mesma pasta do servidor — eles se encontram e colaboram automaticamente.
L7–9
private static final String URL = "jdbc:mysql://..."; private static final String USUARIO = "bd_savir"; private static final String SENHA = "B@nc0D@d0s";
Constantes de configuração do banco
Cada palavra tem um significado preciso:

• private → só a própria classe Conexao pode ver esses valores
• static → existem uma única vez na memória, não se repetem por instância
• final → o valor nunca pode ser alterado depois de definido (é uma constante)
• String → tipo de dado: texto

A URL tem o formato jdbc:mysql://host:porta/banco?parametros. Cada parte instrui o driver JDBC sobre onde conectar e com quais configurações.
Credenciais em texto claro no código-fonte são uma vulnerabilidade de segurança grave. Qualquer pessoa com acesso ao .java vê a senha. A solução correta é usar variáveis de ambiente ou arquivo .properties fora do repositório.
L11–15
static { Class.forName("com.mysql.cj.jdbc.Driver"); }
Bloco estático — executa UMA vez quando a classe é carregada
O bloco static { } é especial: ele roda automaticamente quando a JVM (Java Virtual Machine) carrega a classe na memória pela primeira vez — antes de qualquer método ser chamado.

Class.forName() localiza e registra o driver MySQL na memória. Sem isso, o DriverManager não saberia como se comunicar com um banco MySQL — ele não saberia "falar a língua" do MySQL.
É como instalar um tradutor antes de começar uma reunião com alguém que fala outro idioma. O bloco static instala o "tradutor MySQL" antes de qualquer conversa com o banco.
L20–22
public static Connection getConnection() throws Exception { return DriverManager.getConnection(URL, USUARIO, SENHA); }
getConnection() — abre e devolve um canal ao banco
Este método é o ponto central do projeto — toda classe que precisa do banco chama Conexao.getConnection().

• public static → qualquer classe pode chamar sem criar um objeto Conexao
• Retorna uma Connection — o canal aberto com o banco
• throws Exception → se a conexão falhar, o método lança uma exceção para quem o chamou tratar

Cada chamada abre uma nova conexão. Por isso, toda chamada deve ser seguida por conn.close() para não esgotar as conexões disponíveis.
É como um ramal telefônico centralizado. Qualquer funcionário (classe) liga para o mesmo número (getConnection) e recebe uma linha direta ao banco.
L26–33
public static boolean testarConexao() { try (Connection conn = getConnection()) { if (conn != null) { return true; } } catch (Exception e) { ... } return false; }
testarConexao() — verifica se o banco está acessível antes de logar
O LoginDialog chama este método antes de tentar autenticar o usuário. Se o banco estiver offline, evita que a tela trave esperando por uma conexão que nunca virá.

O try-with-resources (try com parênteses) fecha a conexão automaticamente ao sair do bloco — mesmo que dê erro. É uma versão mais segura de abrir e fechar conexão.

AuditoriaUtil.java — O registrador de eventos

Toda ação importante no sistema é registrada permanentemente em um arquivo texto — login, logout, criação, edição e exclusão de usuários.

AuditoriaUtil.java
private static final String ARQUIVO_LOG = "auditoria.log";             // linha 17
private static final DateTimeFormatter FORMATO =
    DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");               // linha 20

public static void registrar(String login, String evento, String detalhe) {
    String dataHora = LocalDateTime.now().format(FORMATO);              // linha 27
    String linha = dataHora + " | " + login + " | " + evento + " | " + detalhe; // linha 30

    try {
        FileWriter fw = new FileWriter(ARQUIVO_LOG, true);              // linha 33 — append!
        PrintWriter pw = new PrintWriter(fw);
        pw.println(linha);
        pw.close();
    } catch (IOException e) {
        System.err.println("Erro ao gravar auditoria: " + e.getMessage()); // linha 40
    }
}
Classe
public class AuditoriaUtil — sem atributos de instância
Classe utilitária totalmente estática
Esta classe existe apenas para fornecer o método registrar(). Nunca é instanciada com new AuditoriaUtil(). Todos os seus membros são static, o que significa que são chamados diretamente pela classe: AuditoriaUtil.registrar(...).

É chamado de padrão utilitário — uma classe-ferramenta que outras classes usam sem precisar criar objetos.
É como uma impressora de rede compartilhada. Qualquer departamento (classe) pode mandar imprimir (registrar) sem precisar ter uma impressora própria (instanciar).
L20
DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss")
Formatador de data e hora
O DateTimeFormatter define como a data e hora serão escritas no log. O padrão yyyy-MM-dd HH:mm:ss gera datas no formato ISO: 2026-05-14 00:53:54.

• yyyy = ano com 4 dígitos  • MM = mês  • dd = dia
• HH = hora (24h)  • mm = minuto  • ss = segundo
L33
new FileWriter(ARQUIVO_LOG, true)
FileWriter com append=true — nunca apaga o histórico
O segundo parâmetro true ativa o modo append (adicionar). Isso significa que cada nova linha de log é adicionada ao final do arquivo, nunca sobrescrevendo o que já está lá.

Se esse parâmetro fosse false, o arquivo seria apagado e reescrito a cada ação — perdendo todo o histórico. Com true, o log cresce indefinidamente e nunca perde eventos anteriores.
É como um diário que só aceita novas entradas no final — você não pode apagar o que escreveu antes.
L40
System.err.println("Erro ao gravar auditoria: " + e.getMessage());
Tratamento silencioso de erro — o sistema não trava
Se o arquivo de log não puder ser gravado (disco cheio, permissão negada...), o código captura o erro e imprime no console de erro — mas não lança a exceção nem interrompe o sistema.

Essa é uma decisão de design deliberada: a auditoria é importante, mas não tão crítica a ponto de impedir uma operação de cadastro, por exemplo.

System.err (diferente de System.out) é o canal de erros — aparece em vermelho no terminal e pode ser redirecionado separadamente dos logs normais.

Herança
public class FormPrincipal extends JFrame
extends JFrame — herança de uma janela pronta
extends é herança em Java — FormPrincipal herda todo o comportamento e visual de um JFrame (janela do sistema operacional).

Isso significa que FormPrincipal é um JFrame com poderes extras. Ela ganha de graça: barra de título, botões de minimizar/maximizar/fechar, suporte a menus, redimensionamento. Você só precisa adicionar o que é específico do SuperSistema.
É como comprar uma casa pronta (JFrame) e fazer a decoração do jeito que quer (adicionar menus, logo, lógica de login) sem precisar construir a estrutura do zero.
L9–13
private String usuarioLogado = null; private String loginUsuarioLogado = null; private String empresaLogada = null;
Estado da sessão — null = deslogado
Essas três variáveis guardam o estado da sessão ativa. Quando valem null, significa que ninguém está logado. Quando têm valores, a sessão está ativa.

O método aplicarEstadoAutenticacao() verifica constantemente se usuarioLogado != null para decidir o que mostrar no menu.
paintComponent
JPanel painelFundo = new JPanel() { protected void paintComponent(Graphics g) { super.paintComponent(g); Image img = new ImageIcon(..."/logo.jpg").getImage(); g.drawImage(img, 0, 0, getWidth(), getHeight(), this); } };
Classe anônima com override — desenhando o fundo personalizado
Este é um padrão avançado: criamos uma classe anônima (uma subclasse sem nome) que herda de JPanel e substitui o método paintComponent.

Toda vez que o Swing precisa redesenhar o painel (ao redimensionar a janela, por exemplo), ele chama paintComponent. Ao sobrescrevê-lo, garantimos que a logo.jpg é sempre redesenhada cobrindo toda a janela.

super.paintComponent(g) primeiro limpa o painel (obrigatório), depois desenhamos a imagem sobre ele.
É como contratar um pintor que sabe sua técnica padrão mas, neste projeto, você pede que ele também coloque um fundo personalizado toda vez que pintar a parede.
Menu dinâmico
private void aplicarEstadoAutenticacao() { boolean logado = (usuarioLogado != null); itemLogin.setText(logado ? "Logout" : "Logar"); if (logado) { menuBar.add(menuUsuarios); menuBar.add(menuSeguranca); } else { menuBar.remove(menuUsuarios); menuBar.remove(menuSeguranca); } menuBar.revalidate(); menuBar.repaint(); }
Menu dinâmico — adiciona/remove menus conforme o login
Este é o coração da lógica de sessão. O método é chamado em três momentos: ao iniciar (sem login), após login bem-sucedido e após logout.

• logado ? "Logout" : "Logar" → operador ternário: se logado, texto "Logout"; senão, "Logar"
• menuBar.add/remove → adiciona ou remove menus dinamicamente
• revalidate() + repaint() → força o Swing a recalcular e redesenhar a barra de menus imediatamente
Sem revalidate() e repaint(), a mudança nos menus não apareceria visualmente — o Swing não redesenha automaticamente quando você modifica componentes programaticamente.
main
public static void main(String[] args) { SwingUtilities.invokeLater(FormPrincipal::new); }
main + invokeLater — a porta de entrada correta para Swing
SwingUtilities.invokeLater agenda a criação da janela para ser executada na Event Dispatch Thread (EDT) — a thread dedicada ao Swing. Criar componentes Swing fora da EDT pode causar comportamentos imprevisíveis e bugs visuais.

FormPrincipal::new é uma method reference — uma forma compacta de dizer "crie um novo FormPrincipal". É equivalente a () -> new FormPrincipal().

Autenticação

LoginDialog.java — A tela de login com banco de dados

JDialog vs JFrame LoginDialog extende JDialog, não JFrame. A diferença crucial: ao passar true no construtor do JDialog, ele se torna modal — a janela pai (FormPrincipal) fica bloqueada até que o diálogo seja fechado. Isso força o usuário a completar o login antes de fazer qualquer outra coisa.
Campos
private final JComboBox<String> comboEmpresa; private final JTextField campoUsuario; private final JPasswordField campoSenha;
Os três campos de entrada — cada um com um tipo específico
• JComboBox → lista suspensa (SELECT). O <String> é o genérico — indica que esta caixa contém Strings (textos)
• JTextField → campo de texto simples, o usuário vê o que digita
• JPasswordField → campo de senha: mostra ••• em vez das letras digitadas, protegendo visualmente a senha
Validação
if (empresaSel.equals("Selecione uma empresa...")) { return; } if (usr.isEmpty()) { return; } if (sen.isEmpty()) { return; }
Três barreiras de validação antes de tocar o banco
Antes de qualquer consulta ao banco, o código verifica se todos os campos estão preenchidos. Cada return abandona o método imediatamente após mostrar um aviso.

Esse padrão é chamado de "guarda cláusula" — validações antecipadas que evitam código profundamente aninhado. O caminho feliz (tudo válido) fica no final, limpo.
SQL
String sql = "SELECT nome FROM tb_usuarios WHERE login = ? AND senha = ? LIMIT 1"; try (Connection conn = Conexao.getConnection(); PreparedStatement pst = conn.prepareStatement(sql)) { pst.setString(1, usuarioLogin); pst.setString(2, senhaLogin); ResultSet rs = pst.executeQuery(); if (rs.next()) { autenticado = true; } }
A query de autenticação com PreparedStatement
A query busca um usuário com o login E a senha exatos. O LIMIT 1 garante que apenas um resultado seja retornado (otimização).

Os ? são parâmetros — preenchidos por setString(1, ...) e setString(2, ...). Isso é crucial: o driver JDBC escapa automaticamente qualquer caractere especial, impedindo SQL Injection.

rs.next() retorna true se encontrou pelo menos um resultado — se achou, o login está correto.
É como uma catraca que só abre quando você apresenta o crachá exato (login + senha). O PreparedStatement é o leitor de crachá que não se deixa enganar por crachás falsificados (SQL Injection).
Getters
public boolean isAutenticado() { return autenticado; } public String getUsuario() { return usuario; } public String getLoginAutenticado() { return loginDigitado; } public String getEmpresa() { return empresa; }
Getters — a interface pública entre LoginDialog e FormPrincipal
Depois que o LoginDialog fecha, o FormPrincipal precisa saber o resultado. Como as variáveis internas são private, ele acessa através desses métodos públicos de leitura (getters).

Esse é o princípio de encapsulamento: os dados ficam protegidos internamente, mas valores relevantes são expostos de forma controlada.

FormUsuariosListar.java — O hub do CRUD

Esta é a janela central do CRUD. Exibe todos os usuários em uma tabela e oferece botões para todas as operações. É o "gerenciador de arquivos" do sistema.

JTable

JTable somente leitura com DefaultTableModel customizado
O DefaultTableModel é criado com uma classe anônima que sobrescreve isCellEditable para sempre retornar false. Isso impede que o usuário edite dados diretamente na tabela — as edições só acontecem pelo formulário adequado.

O construtor DefaultTableModel(colunas, 0) cria a tabela com os cabeçalhos definidos e zero linhas de dados — as linhas serão adicionadas pelo método carregarUsuarios().
Loop
JButton[] botoes = {btnIncluir, btnEditar, btnExcluir, btnAtualizar, btnSair}; for (JButton b : botoes) { b.setPreferredSize(tamanhoPadrao); b.setMinimumSize(tamanhoPadrao); b.setMaximumSize(tamanhoPadrao); barra.add(b); }

Em vez de repetir as mesmas 4 linhas para cada botão, o código os coloca em um array e usa um for-each (para cada botão no array, faça...). Este é o princípio DRY (Don't Repeat Yourself) — não repetir código.

setPreferredSize + setMinimumSize + setMaximumSize juntos fixam o tamanho exato do botão — o LayoutManager não pode nem aumentar nem diminuir.
Mouse

Duplo clique na linha abre formulário de edição

e.getClickCount() == 2 detecta duplo clique. Ao clicar duas vezes numa linha, o sistema abre automaticamente o formulário de edição com aquele usuário — uma experiência de usuário mais fluida.
É como no Windows Explorer: duplo clique em um arquivo abre ele. Aqui, duplo clique em uma linha de usuário abre o formulário de edição.

CRUD — Inclusão e Edição

FormUsuarioEditar.java — Um formulário, dois modos

Design inteligente: um formulário para dois casos de uso Ao receber usuarioId = 0, o formulário entra em modo inclusão e executa um INSERT. Com qualquer ID maior que zero, entra em modo edição e carrega os dados do banco para exibir, executando um UPDATE ao salvar. Mesma tela, dois comportamentos — elimina código duplicado.
Construtor
super(janelaPai, usuarioId == 0 ? "Incluir Usuário" : "Editar Usuário", true);
Título dinâmico baseado no modo
super() chama o construtor da classe pai (JDialog) com três argumentos:
• janelaPai → a janela que está "abrindo" este diálogo (FormUsuariosListar)
• título → determinado por operador ternário — "Incluir" se id=0, "Editar" caso contrário
• true → torna o diálogo modal (bloqueia a janela pai)
GridBag
GridBagConstraints gbc = new GridBagConstraints(); gbc.insets = new Insets(6, 6, 6, 6); gbc.fill = GridBagConstraints.HORIZONTAL; gbc.gridx = 0; gbc.gridy = 0; // coluna 0, linha 0 painel.add(new JLabel("Nome completo:"), gbc); gbc.gridx = 1; gbc.weightx = 1; painel.add(campoNome, gbc);
GridBagLayout — posicionamento preciso em grade
O GridBagLayout é o mais poderoso dos layout managers. Cada componente tem um GridBagConstraints que define sua posição:

• gridx/gridy → coluna e linha na grade
• insets → espaçamento externo (topo, esquerda, baixo, direita)
• fill = HORIZONTAL → o componente se expande para preencher o espaço horizontal disponível
• weightx = 1 → "este componente pode crescer horizontalmente"

if (usuarioId == 0) { sql = "INSERT INTO tb_usuarios (nome, login, senha, email) VALUES (?, ?, ?, ?)"; } else { sql = "UPDATE tb_usuarios SET nome=?, login=?, senha=?, email=? WHERE usuario_id=?"; stmt.setInt(5, usuarioId); } stmt.executeUpdate();
Bifurcação INSERT vs UPDATE baseada no ID
O mesmo método salvar() executa operações diferentes dependendo do usuarioId:

• INSERT adiciona uma nova linha ao banco — não precisa do ID (o banco gera automaticamente via AUTO_INCREMENT)
• UPDATE modifica uma linha existente — precisa do WHERE usuario_id = ? para saber qual linha atualizar

executeUpdate() executa tanto INSERT quanto UPDATE — retorna o número de linhas afetadas.
Duplicate
if (mensagem != null && mensagem.contains("Duplicate entry")) { JOptionPane.showMessageDialog(..., "Este login já está em uso."...); campoLogin.requestFocus(); }
Tratamento específico de login duplicado
A coluna login na tabela tem uma constraint UNIQUE — o banco rejeita logins repetidos. Quando isso acontece, o MySQL lança uma exceção com a mensagem "Duplicate entry".

O código intercepta essa mensagem específica e exibe um aviso mais amigável que "Erro genérico de banco". requestFocus() coloca o cursor automaticamente no campo login para facilitar a correção.

Esquema MySQL — A estrutura dos dados

tb_usuarios — DDL
CREATE TABLE tb_usuarios (
    usuario_id INT          NOT NULL AUTO_INCREMENT,  -- PK autogerada
    nome       VARCHAR(100) NOT NULL,               -- nome completo
    login      VARCHAR(50)  NOT NULL UNIQUE,         -- sem duplicatas!
    senha      VARCHAR(100) NOT NULL,               -- ⚠ texto plano
    email      VARCHAR(150)     NULL,               -- opcional
    PRIMARY KEY (usuario_id)
);
PK
usuario_id INT NOT NULL AUTO_INCREMENT
Chave primária com auto incremento
PRIMARY KEY identifica cada linha de forma única. AUTO_INCREMENT faz o MySQL gerar automaticamente o próximo número disponível (1, 2, 3...) ao inserir um novo usuário — você nunca precisa definir o ID manualmente.
UNIQUE
login VARCHAR(50) NOT NULL UNIQUE
Constraint UNIQUE — o banco garante logins únicos
A constraint UNIQUE faz o banco rejeitar qualquer INSERT ou UPDATE que tente inserir um login já existente. É uma garantia de integridade no nível do banco — mesmo que o código Java esqueça de verificar, o banco protege.

🧠 Quiz — Você entendeu o SuperSistema?

1. Por que o LoginDialog usa JDialog em vez de JFrame?
APorque JDialog é mais moderno que JFrame
BPara bloquear a janela principal enquanto o login está aberto (comportamento modal)
CPorque JFrame não suporta campos de senha
DPara economizar memória no sistema
✅ Correto! Com true no construtor do JDialog, ele se torna modal — a janela pai (FormPrincipal) fica bloqueada até o diálogo fechar, forçando o usuário a completar o login antes de qualquer outra ação.
❌ A razão principal é o comportamento modal: o JDialog com modal=true bloqueia a janela pai até ser fechado. Isso é essencial para um fluxo de autenticação correto.
2. Por que o FileWriter em AuditoriaUtil é criado com o segundo parâmetro true?
APara criar o arquivo automaticamente se não existir
BPara fazer o arquivo crescer mais rápido
CPara ativar o modo append — novas linhas são adicionadas ao final, sem apagar o histórico
DPara sincronizar com o banco de dados
✅ Exato! new FileWriter(arquivo, true) abre em modo append. Sem esse true, o arquivo seria apagado e reescrito em cada nova ação, destruindo todo o histórico anterior.
❌ O segundo parâmetro true ativa o modo append: cada nova linha é adicionada ao final do arquivo, nunca apagando o que já foi registrado.
3. O que o método menuBar.revalidate() faz após adicionar/remover menus?
ASalva as configurações do menu no banco de dados
BVerifica se os menus têm permissão para aparecer
CForça o Swing a recalcular o layout e redesenhar a barra — sem isso, a mudança não apareceria na tela
DReinicia a sessão do usuário
✅ Perfeito! O Swing não redesenha automaticamente quando você modifica componentes programaticamente. revalidate() recalcula o layout e repaint() redesenha visualmente — os dois juntos garantem que a mudança seja imediatamente visível.
❌ revalidate() + repaint() são necessários porque o Swing não reflete mudanças programáticas automaticamente — você precisa pedir explicitamente que ele redesenhe o componente.
4. Por que usar PreparedStatement em vez de concatenar strings para montar o SQL?
APreparedStatement é mais rápido de digitar
BProtege contra SQL Injection — os ? são escapados automaticamente pelo driver JDBC
CPorque VARCHAR(100) não aceita strings concatenadas
DPara funcionar com MySQL versão 8 e superior
✅ Correto! Se você concatenar diretamente (ex: "WHERE login = '" + input + "'"), um usuário mal-intencionado pode digitar ' OR '1'='1 e acessar qualquer conta. O PreparedStatement escapa os parâmetros antes de enviá-los, bloqueando esse ataque.
❌ A razão principal é segurança: SQL Injection. Concatenar input do usuário diretamente no SQL permite ataques que burlam a autenticação ou apagam dados do banco.
Análise crítica

🔐 Pontos de Segurança — Limitações conhecidas

O SuperSistema é um projeto didático funcional, mas possui vulnerabilidades importantes para quem for evoluí-lo:

🔑

Senhas em texto plano

As senhas são salvas diretamente na tb_usuarios sem hash. Se o banco vazar, todas as senhas ficam expostas. Solução: aplicar BCrypt ou SHA-256+salt antes de persistir.

🔒

Credenciais no código-fonte

A URL, usuário e senha do banco estão em texto claro em Conexao.java. Qualquer pessoa com acesso ao repositório vê tudo. Solução: variáveis de ambiente ou config.properties no .gitignore.

🚪

Sem limite de tentativas

É possível tentar login ilimitadas vezes sem bloqueio — suscetível a ataque de força bruta. Solução: bloquear após N tentativas falhas e registrar IPs suspeitos.

👤

Sem controle de permissões

Qualquer usuário logado acessa todos os menus (Usuários e Segurança). Solução: adicionar coluna perfil ENUM('admin','operador') e exibir menus conforme o perfil.

📝

Log editável manualmente

O auditoria.log é um arquivo texto comum — pode ser editado ou apagado. Solução: gravar em tabela no banco com constraint de integridade ou usar log assinado.

🔓

Conexão sem SSL

O parâmetro useSSL=false desabilita criptografia na comunicação com o banco. Dados trafegam em texto claro na rede. Solução: habilitar SSL/TLS na conexão JDBC.
