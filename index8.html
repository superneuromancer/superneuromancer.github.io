01 — SISTEMA CORPORATIVO

O que é um Sistema Corporativo?

Até agora trabalhamos o banco de dados de forma isolada — comandos SQL direto no terminal. Agora vamos pensar como empresas reais pensam: o banco não é um fim em si mesmo. Ele é o alicerce de um sistema corporativo.

Um sistema corporativo é uma aplicação desenvolvida para atender processos organizacionais reais. Toda ação do usuário — cadastrar um cliente, consultar um pedido, atualizar um endereço — gera comandos no banco. O banco é invisível para o usuário, mas presente em cada operação.

🎓
Sistema Acadêmico
Ex.: alunos, notas, turmas

Cadastro de alunos, lançamento de notas, controle de frequência — tudo em banco.

🏥
Sistema Hospitalar
Ex.: prontuário, consultas

Pacientes, médicos, exames, prescrições — dados críticos persistidos com consistência.

🛍️
Sistema de Pedidos
Ex.: e-commerce, delivery

Produtos, estoque, clientes, pedidos — relações complexas entre múltiplas tabelas.

🏢
ERP Empresarial
Ex.: SAP, TOTVS, Odoo

Integra finanças, RH, logística em um único banco — máxima complexidade relacional.

🏦
Aplicativo Bancário
Ex.: contas, transferências

Transações atômicas, saldo em tempo real — onde a consistência do banco é vital.

📊
Dashboard Analytics
Ex.: relatórios, KPIs

Leitura intensiva de dados agregados — SQL avançado com GROUP BY, JOINs e índices.

🏗️ Mudança de nível A diferença entre um estudante de banco de dados e um profissional de mercado é essa: o estudante aprende SQL. O profissional aprende a conectar SQL a um sistema real. Essa aula faz essa transição. O banco que você aprendeu a consultar agora vai responder a requisições HTTP vindas de aplicações rodando em produção.
02 — ARQUITETURA

Arquitetura Simplificada

Todo sistema corporativo segue a mesma lógica: há uma camada que o usuário vê (frontend), uma camada que processa regras (API), e uma camada que persiste dados (banco). A API é o intermediário inteligente — ela nunca deixa o banco exposto diretamente ao mundo.

Arquitetura de 3 Camadas — Sistema Corporativo ────────────────────────────────────────────────────────────── ┌─────────────────────────────┐ │ CAMADA 1 — CLIENTE │ ← navegador, app mobile, Postman │ React, HTML, Vue, Flutter │ o usuário interage aqui └──────────────┬──────────────┘ │ HTTP Request (GET /clientes) ▼ ┌─────────────────────────────┐ │ CAMADA 2 — API REST │ ← Node.js + Express, porta 3000 │ Regras de negócio, validação │ processa a requisição aqui └──────────────┬──────────────┘ │ SQL Query (SELECT * FROM cliente) ▼ ┌─────────────────────────────┐ │ CAMADA 3 — BANCO DE DADOS │ ← PostgreSQL, porta 5432 │ Persistência, integridade │ armazena os dados aqui └─────────────────────────────┘ Fluxo: Usuário → Request HTTP → API processa → SQL → Banco → Resposta → Usuário

Por que a API não deixa o banco exposto?

CenárioBanco Diretamente ExpostoBanco via API REST
AutenticaçãoQualquer um com credenciais acessa tudoA API valida tokens JWT, sessões
Validação de dadosDados inválidos entram diretoA API valida antes de gravar
Controle de acessoImpossível por usuário/perfilA API filtra por papel e permissão
SQL InjectionVulnerável se o cliente montar SQLA API usa parâmetros, protegendo o banco
ConclusãoA API é o guardião do banco. Nenhum cliente deve falar diretamente com o PostgreSQL.
💡 Ideia central da aula Banco de dados não é um fim em si mesmo. Ele é a memória de longo prazo de um sistema corporativo. A API é o cérebro — ela decide o que pode e o que não pode ser feito com essa memória. Você precisa entender os dois para construir sistemas reais.
03 — CRUD

CRUD: O Coração da Aplicação

CRUD é o acrônimo das quatro operações fundamentais de qualquer sistema que persiste dados. Não importa se é um ERP de R$ 10 milhões ou um app de lista de tarefas — todos giram em torno dessas quatro ações.

➕
C — Create
Criar · INSERT · POST

Inserir um novo registro no banco. Um cliente se cadastra, um produto é adicionado ao estoque, um pedido é criado.

🔍
R — Read
Consultar · SELECT · GET

Buscar e retornar dados existentes. Listar todos os clientes, consultar um produto por ID, exibir o histórico de pedidos.

✏️
U — Update
Atualizar · UPDATE · PUT

Modificar um registro existente. Alterar o email do cliente, atualizar o preço de um produto, mudar o status de um pedido.

🗑️
D — Delete
Excluir · DELETE · DELETE

Remover um registro do banco. Deletar uma conta, remover um item de um carrinho, cancelar e excluir um pedido.

Visão prática Quando você abre o Instagram e carrega o feed, isso é um Read. Quando você posta uma foto, é um Create. Quando edita a legenda, é um Update. Quando deleta a postagem, é um Delete. Toda interface que você já usou é construída sobre essas quatro operações.

04 — ESTRUTURA SQL

Estrutura SQL da Aplicação

Antes de escrever uma linha de Node.js, definimos a estrutura do banco. O arquivo schema.sql é o contrato entre a aplicação e o banco — ele define exatamente quais dados existem e como estão organizados.

schema.sql · tabela de clientes 
CREATE TABLE cliente (
    id        SERIAL       PRIMARY KEY,   -- auto-incremento, chave primária
    nome      VARCHAR(100),               -- nome completo do cliente
    email     VARCHAR(100),               -- endereço de email
    telefone  VARCHAR(20)                 -- telefone com DDD
);

-- SERIAL: PostgreSQL cria automaticamente 1, 2, 3, 4...
-- PRIMARY KEY: garante unicidade — dois clientes não terão o mesmo id
-- VARCHAR(n): string com limite de n caracteres

Anatomia da tabela

Tabela: cliente ┌──────┬──────────────────────┬────────────────────────┬──────────────────┐ │ id │ nome │ email │ telefone │ │ SERIAL│ VARCHAR(100) │ VARCHAR(100) │ VARCHAR(20) │ │ PK │ │ │ │ ├──────┼──────────────────────┼────────────────────────┼──────────────────┤ │ 1 │ Carlos Souza │ carlos@email.com │ 85911110001 │ │ 2 │ Maria Lima │ maria@email.com │ 85922220002 │ │ 3 │ João Ferreira │ joao@email.com │ 85933330003 │ └──────┴──────────────────────┴────────────────────────┴──────────────────┘ O campo id é gerado automaticamente pelo PostgreSQL. A aplicação nunca precisa enviar o id ao inserir — apenas nome, email e telefone.
Por que SERIAL e não INTEGER? SERIAL é um atalho do PostgreSQL que cria automaticamente uma sequência e usa o próximo número disponível como valor padrão. Você nunca precisa calcular o próximo ID na aplicação — o banco faz isso por você. Em sistemas com múltiplas requisições simultâneas, isso garante que dois clientes não recebam o mesmo ID.
05 — REST API

REST API: Mapeando CRUD para HTTP

REST (Representational State Transfer) é uma convenção para criar APIs usando o protocolo HTTP. A beleza do REST é que ele mapeia naturalmente as quatro operações CRUD para os quatro verbos HTTP — e a URL define o quê está sendo operado.

CRUD → REST: o mapeamento padrão da indústria ──────────────────────────────────────────────────────────── CRUD Método HTTP URL O que faz ──────── ─────────── ────────────────── ──────────────────────────── Create POST /clientes cria um novo cliente Read GET /clientes lista todos os clientes Read GET /clientes/:id busca um cliente por ID Update PUT /clientes/:id atualiza um cliente Delete DELETE /clientes/:id exclui um cliente ──────────────────────────────────────────────────────────── :id = parâmetro dinâmico na URL → /clientes/1 /clientes/42 /clientes/999

Como o Express lê esses verbos

No Express, cada verbo HTTP vira um método: app.get(), app.post(), app.put(), app.delete(). A estrutura é sempre a mesma:

JavaScript · estrutura de uma rota Express 
// Padrão de toda rota: app.MÉTODO(URL, função)

app.get('/clientes', async (req, res) => {
    // req = requisição (o que veio do cliente)
    // res = resposta (o que mandamos de volta)
    // async porque vamos esperar o banco responder

    const result = await pool.query('SELECT * FROM cliente');
    res.json(result.rows);  // envia o resultado como JSON
});
VerboIdempotente?Tem body?Retorno típico
POSTNão — 2 POSTs criam 2 registrosSim — dados do novo recurso201 Created + recurso criado
GETSim — seguro para chamar várias vezesNão — apenas parâmetros na URL200 OK + dados

06 — ESTRUTURA DO PROJETO

Estrutura do Projeto

Um projeto bem organizado separa responsabilidades: um arquivo cuida da conexão ao banco, outro cria o servidor, outro define o schema. Essa separação torna o código mais fácil de manter, testar e evoluir.

Estrutura de pastas — projeto CRUD corporativo ──────────────────────────────────────────────── meu-sistema/ ├── package.json ← metadados + dependências (express, pg) ├── db.js ← configuração da conexão com o PostgreSQL ├── server.js ← servidor Express + todas as rotas CRUD └── schema.sql ← script SQL para criar as tabelas ───────────────────────────────────────────────── Separação de responsabilidades: · db.js → COMO conectar ao banco (credenciais, pool) · server.js → O QUE a API faz (rotas, lógica) · schema.sql→ QUAL é a estrutura dos dados

Instalando as dependências

terminal
# 1. Inicializa o projeto (cria package.json) $ npm init -y # 2. Instala as duas únicas dependências necessárias $ npm install express pg # · express → cria o servidor HTTP e gerencia rotas # · pg → driver Node.js para o PostgreSQL added 67 packages in 2.1s
Express Framework minimalista para criar servidores HTTP em Node.js. Com poucas linhas você define rotas, middlewares e inicia o servidor. É o padrão da indústria para APIs REST em JavaScript.
pg (node-postgres) Driver oficial para conectar Node.js ao PostgreSQL. O objeto Pool gerencia um conjunto de conexões reutilizáveis — muito mais eficiente do que abrir e fechar uma conexão por requisição.
07 — IMPLEMENTAÇÃO

Implementação Completa

Agora construímos o sistema peça por peça. Começamos pela conexão ao banco, depois criamos o servidor e, por último, cada uma das quatro rotas CRUD — cada uma com seu SQL parametrizado correspondente.

Passo 1 — db.js: conexão com o PostgreSQL

db.js · Pool de conexões 
const { Pool } = require('pg');

const pool = new Pool({
    user:     'postgres',    // usuário do banco
    host:     'localhost',   // endereço (local em dev)
    database: 'postgres',    // nome do banco de dados
    password: 'SUA_SENHA',   // ← troque pela sua senha real
    port:     5432            // porta padrão do PostgreSQL
});

// O Pool reutiliza conexões abertas.
// Sem Pool: abre conexão → query → fecha → repete (lento)
// Com Pool: mantém conexões prontas → muito mais eficiente

module.exports = pool;  // exporta para ser usado no server.js

Passo 2 — server.js: servidor base

server.js · servidor Express (base) 
const express = require('express');
const pool    = require('./db');      // importa a conexão

const app = express();
app.use(express.json());  // habilita leitura de JSON no body das requisições

// ... rotas CRUD aqui (ver abaixo) ...

app.listen(3000, () => {
    console.log('Servidor rodando na porta 3000');
});

Passo 3 — as quatro rotas CRUD

server.js · Create — POST /clientes 
app.post('/clientes', async (req, res) => {
    const { nome, email, telefone } = req.body;  // desestrutura o JSON recebido

    const result = await pool.query(
        'INSERT INTO cliente (nome, email, telefone) VALUES ($1, $2, $3) RETURNING *',
        [nome, email, telefone]  // ← parâmetros seguros (evita SQL Injection!)
    );

    res.status(201).json(result.rows[0]);  // retorna o registro criado com o id
});
server.js · Read — GET /clientes 
app.get('/clientes', async (req, res) => {
    const result = await pool.query(
        'SELECT * FROM cliente ORDER BY id'
    );

    res.json(result.rows);  // retorna um array de todos os clientes
});
server.js · Update — PUT /clientes/:id 
app.put('/clientes/:id', async (req, res) => {
    const { id }                    = req.params;  // id vem da URL: /clientes/42
    const { nome, email, telefone } = req.body;   // novos dados vêm no body

    const result = await pool.query(
        'UPDATE cliente SET nome=$1, email=$2, telefone=$3 WHERE id=$4 RETURNING *',
        [nome, email, telefone, id]
    );

    res.json(result.rows[0]);  // retorna o cliente com os dados atualizados
});
server.js · Delete — DELETE /clientes/:id 
app.delete('/clientes/:id', async (req, res) => {
    const { id } = req.params;

    await pool.query(
        'DELETE FROM cliente WHERE id = $1',
        [id]
    );

    res.json({ mensagem: 'Cliente excluído com sucesso' });
});
✓ O padrão que se repete Perceba que todas as rotas seguem o mesmo padrão: (1) extrair dados da requisição (req.body ou req.params), (2) executar uma query SQL com parâmetros, (3) retornar o resultado como JSON. Quando você entender esse padrão, consegue criar qualquer rota CRUD para qualquer tabela.
08 — SEGURANÇA

Segurança: SQL Injection

SQL Injection é a vulnerabilidade mais explorada em aplicações que usam banco de dados. Ela permite que um atacante injete comandos SQL maliciosos na sua query — podendo destruir dados, burlar autenticação ou vazar todo o banco. A boa notícia: a solução é simples e você já está usando.

⛔ Código vulnerável — NUNCA faça isso Montar SQL por concatenação de strings abre a porta para ataques devastadores:

const sql = 'SELECT * FROM cliente WHERE id = ' + req.params.id;

Se um atacante enviar id = 1 OR 1=1; DROP TABLE cliente; --, a query vira:
SELECT * FROM cliente WHERE id = 1 OR 1=1; DROP TABLE cliente; --

Resultado: toda a tabela é apagada. Em produção, isso é um incidente crítico.
✗ VULNERÁVEL — concatenação direta ───────────────────────────────────────────────────────────── pool.query('SELECT * FROM cliente WHERE id = ' + id) Ataque: id = "1 OR 1=1; DROP TABLE cliente; --" Query resultante: SELECT * FROM cliente WHERE id = 1 OR 1=1; DROP TABLE cliente; -- ↑ retorna TODOS os registros + destrói a tabela ───────────────────────────────────────────────────────────── ✓ SEGURO — parâmetros $1, $2, $3... ───────────────────────────────────────────────────────────── pool.query('SELECT * FROM cliente WHERE id = $1', [id]) O pg trata o valor de $1 como dado puro, nunca como SQL. O atacante envia "1 OR 1=1;..." mas o banco lê como string literal: busca por id igual ao texto "1 OR 1=1;..." → nenhum resultado → seguro.

A regra de ouro

PráticaVulnerável?Exemplo
Concatenação com +⛔ Sim'WHERE id = ' + id
Template literal ${}⛔ Sim`WHERE id = ${id}`
Parâmetros $1, $2...✓ Não'WHERE id = $1', [id]
Regra absolutaNenhum dado do usuário deve ir para o SQL por concatenação. Sempre use parâmetros.
Por que $1, $2... protege? Quando você usa parâmetros, o driver pg envia a query e os valores separadamente ao PostgreSQL. O banco processa a estrutura SQL primeiro, e depois substitui os $1, $2 pelos valores — que são tratados como dados literais, nunca como comandos. É impossível injetar SQL por essa via.

10 — PRÓXIMOS PASSOS

Próximos Passos

Você dominou o CRUD básico. Sistemas reais adicionam camadas sobre essa fundação — cada uma resolvendo um problema específico que você vai encontrar em produção.

Próximo imediato
Validação de Entradas

Antes de inserir, verificar se o nome não está vazio, se o email tem formato válido, se o telefone tem o tamanho certo. Libs como joi ou zod tornam isso declarativo.

joi · zod · express-validator
Nível Intermediário
Autenticação JWT

Proteger as rotas com tokens JWT — só usuários autenticados podem criar, atualizar ou deletar. A leitura pode ser pública. Base de qualquer sistema com login.

jsonwebtoken · bcrypt
Nível Intermediário
Relacionamentos e JOINs

Um sistema real tem múltiplas tabelas relacionadas — clientes têm pedidos, pedidos têm itens, itens têm produtos. Chaves estrangeiras e JOINs conectam esses dados.

FOREIGN KEY · JOIN · CASCADE
Nível Avançado
Variáveis de Ambiente

Nunca suba senha de banco para o GitHub. O arquivo .env com a lib dotenv mantém credenciais fora do código-fonte — prática obrigatória em produção.

dotenv · .gitignore · segurança

Fluxo completo revisitado

1
Usuário envia um cadastro O frontend coleta nome, email e telefone e faz POST /clientes com JSON no body.
2
A API recebe o JSON O Express parseia o body. A rota app.post('/clientes') é ativada. Os dados são extraídos de req.body.
3
A API executa o INSERT com parâmetros pool.query('INSERT INTO cliente ... VALUES ($1,$2,$3)', [nome,email,telefone]) — seguro contra SQL Injection.

5
A API devolve a resposta O Express envia res.status(201).json(result.rows[0]) — o cliente criado com o ID atribuído, de volta para o frontend.
